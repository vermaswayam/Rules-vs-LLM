## Dataset and ground truth

NYC Open Data `erm2-nwe9`, requests created in calendar 2023. Saved sample: **12,000** rows, 1,000 per month; the server population-count query returned **3,224,723** at acquisition. Counts below describe the sample, not the census. These are deterministic monthly coverage slices, not a representative random sample. Exact queries, retrieval time and SHA256 are in `data/nyc/manifest.json`.

Disjoint SHA256-key split: 7,180 training, 4,820 holdout; 4,816 structurally screened holdout rows; fixed benchmark control cohort 1,200. Reference relationships and distributions are fit only on training. Socrata numeric strings are explicitly normalized before the contract boundary; ZIP remains a string. Injection labels live outside the rows and are never sent to a detector.

**False-alarm caveat:** controls are structurally screened real rows, not exhaustively human-labelled clean semantic data. We therefore report the control-alert rate as a proxy FAR. A novel category pair or an agency phone number may be legitimate. Reporting these as proven false positives or proven personal-data leaks would be unjustified. Genuine clean semantic FAR needs a reviewed holdout. Hard structural checks do have an explicit contract.

## Injection protocol and metrics

Each corruption runs at 1%, 5% and 10%, using seeds 17, 29 and 44, against the same fixed holdout cohort. Rates are targets; eligible-row limits and append-only duplicates produce recorded actual rates. A renamed/dropped column is a batch event and affects every row, so its 1% event switch is not described as 1% damaged cells. Date changes occupy a contiguous mid-batch segment. Duplicate labels mark only the added copies. Near-duplicates change the key, timestamp and text. The PII variants include reserved-domain emails, fictitious 555 numbers, explicitly labelled names and contextual names.

Recall = alerted injected rows / injected rows. Control proxy FAR = alerted control rows / control rows, for that problem. Raw files include TP/FN, actual rates, per-rate results, batch-detection rate and descriptive Wilson intervals. Correlated null-spike rows and schema events make row-wise intervals optimistic; independent batch/customer resampling is needed for deployment confidence.

Throughput and CPU cost below measure execution of the **entire detector family** on each workload, not just the named check. Do not add the twelve per-problem costs together. CPU cost is measured process time projected at USD .04/core-hour. Local rules/statistics use no model tokens; this is not a claim of zero infrastructure cost.

## Hybrid pipeline, end to end

Rules evaluate hard schema/type/time/geography and identity invariants, plus normalized near-duplicate candidates. Statistics monitor agency null-rate shifts. The fuzzy near-duplicate baseline remains experimental: it did not improve injection recall and raised more control alerts in this run. Category/ZIP, status-text and personal-data suspicions stay visible as `needs_review` candidates. A Gemini batch can add supporting review, with a hard cap of 32 candidate rows. Missing/quota-limited model evidence leaves the row in review; it does not silently pass it or assert that it is corrupt. No LLM can overrule a hard arithmetic/schema constraint.

The mixed benchmark contains 1,220 rows in disjoint corruption segments, preventing one mutation from erasing another. End-to-end wall time: 0.987 seconds; throughput: 1,236 rows/s. ## Scale design: 50 million rows/day, 120 customers (under two pages)

**Capacity is a projection, not a distributed benchmark.** Assume 50 million rows total across 120 customers, not per customer: average 578.7 rows/s. At the measured mixed throughput, one serial process would need 11.24 hours/day. The laptop figure excludes source/network/storage, scheduler overhead, cross-batch state and burst load. A tenfold arrival burst is 5,787.0 rows/s. Partition by customer and producer; size workers from a real burst/load test and leave headroom.

**Rules:** Define a versioned contract per customer/producer rather than a global 311 schema. Column alias changes are reviewed schema migrations. Hard failures quarantine affected partitions before dashboard publication; missing-but-allowed fields remain null. Compile cheap predicates into vectorized columnar batches. Cache immutable reference relations, and attach contract/source version, row key and observed value to every alert.

**Statistics:** Maintain agency/producer-specific windows and minimum-support requirements. Use training snapshots plus streaming counts, not a continually retrained baseline that can absorb corruption. Monitor multiple-testing alert volume, seasonal changes and schema drift. For near-duplicates, use keyed time-window state and content hashes; the laptop implementation blocks by agency/problem/address and inspects at most 25 candidates, so it can miss long or cross-batch duplicates. Distributed state retention and late arrivals need explicit policies.

**LLM:** Keep it out of hard invariants. The supplied evidence does not yet establish a Gemini advantage, so mandatory LLM review is not a justified launch dependency. Use it as an experiment on ambiguous semantic candidates and a blinded sample. Batch and deduplicate repeated narratives, redact sensitive customer content before any production external review, cap tokens/requests per tenant, and queue work during quota outages. The model's text and a human adjudication are separate records.

**Cost scenario:** A cap of 32 reviewed rows per 1,200 source rows permits up to 1,333,333 reviews/day. If amortized context/input is 500 tokens and output is 30 tokens per reviewed row, at the explicitly configured USD .30/2.50 per million tokens that is USD 300/day for model tokens. These are planning assumptions, not measured Gemini usage. At 120 customers the mean is USD 2.50/customer/day only if volumes are equal. A 0.1% random audit means 50,000 rows/day and USD 11.25/day under the same token assumptions. Real cost must use the recorded request overhead, retries and candidate prevalence.

**Alert quality:** Route errors, warnings and review candidates differently. Publish dashboards only after hard checks pass; show or hold semantic candidates according to each customer's stated quality SLA. Review examples from both alerted and unalerted rows. Measure true FAR, recall and queue completion against blinded human labels before claiming semantic correctness. Injection recall is useful for regression and can be high for simple templates while real-world recall remains unknown.
